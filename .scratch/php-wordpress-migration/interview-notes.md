# Архив интервью: миграция на PHP и WordPress

## Подтверждённые требования

- Переписать текущий проект на PHP 8 и WordPress для виртуального хостинга Timeweb.
- WordPress строго 6.7.1, как в установленном пользователем комплекте Timeweb.
- Развёртывание должно допускать загрузку подготовленных файлов по FTP.
- Для локальной проверки использовать MySQL в Docker.
- Сохранить бизнес-логику с явно согласованными исключениями: стандартная роль WordPress «Автор» вместо прежних прав Strapi; формат редактора публикаций уточняется с учётом штатных возможностей WordPress.
- Переписывание публичной части сайта имеет первый приоритет в плане реализации.
- Разрабатывать PHP-версию рядом с существующей; старые файлы не удалять.
- Проверить готовность компьютера к локальной разработке.
- Сохранить текущий внешний вид, мобильное представление, URL и интерактивное поведение. CSS и небольшой JavaScript допускаются; новая версия не должна требовать серверного Node.js.
- На первом этапе через WordPress редактируются только публикации; другие разделы остаются встроенными в код.
- Старые публикации, черновики и медиа Strapi переносить не требуется. Локальная MySQL начинается с чистой базы.
- На хостинге WordPress уже установлен и есть база с данными. Пользователь хочет впоследствии использовать её штатным способом; устройство и состав этой базы ещё не проверены.
- Пользователь уточнил, что WordPress на хостинге чистый, предположительно с базовой настройкой. Техническая проверка установки остаётся задачей агента; определять её устройство пользователь не обязан. Рабочий вариант — загрузить и активировать тему/плагин в существующей установке, сохраняя её подключение к БД и пользователей.
- Использовать стандартную роль WordPress `author` без расширения до прав редактирования чужих публикаций. Автор может создавать, редактировать, удалять и публиковать собственные записи и загружать файлы; это согласованное отличие от прежней роли Strapi.
- Пользователь выбрал готовый Markdown-плагин и потребовал бесплатность. Кандидат — бесплатный Markup Markdown из каталога WordPress.org; платная поддержка автора не является необходимой для использования редактора.
- Локально WordPress, PHP, веб-сервер и MySQL запускаются через Docker.
- Подготовить очень краткую инструкцию применения изменений и пересборки для самостоятельной проверки пользователем. Предпочесть подключение исходников темы и плагина в контейнер: обычные правки PHP/CSS/JS видны после обновления страницы; пересборка нужна при изменении образа/зависимостей. Конкретные проверенные команды появятся при реализации.

## Состояние обсуждения

Идёт интервью по навыку grill-with-docs (grilling + domain-modeling).
Предметные вопросы интервью закрыты: выбран готовый бесплатный Markdown-плагин; пользователь подтвердил, что авторы не будут пользоваться скринридером. Markup Markdown выбран для проверки на целевом стеке; его совместимость пока не подтверждена запуском. Подготовлен проект плана `plan.md` для итогового подтверждения. Предлагаемое размещение — `wordpress/` со своим Docker-окружением. Фактические версии и настройки хостинга остаются задачами технической проверки, а не вопросами к пользователю о предпочтениях.
Реализация начнётся после подтверждения общего понимания по завершении интервью.

## Обнаруженные ограничения

- ADR 0001 закрепляет Strapi как источник публикаций. Переход на WordPress потребует нового решения, явно заменяющего эту часть ADR; правила публикации и демонстрационных материалов нужно сохранить.
- `docs/hosting.md` уже существовал как неотслеживаемый файл до начала работы; не изменять его без отдельной необходимости.
- Панель https://hosting.timeweb.ru/ требует входа; фактические версии PHP/MySQL аккаунта не проверены.
- Текущая CMS владеет только публикациями; другие страницы и материалы встроены в код. Перенос всего содержимого в редактор WordPress был бы отдельным расширением задачи.
- В текущем поведении нет формы отправки, карты, контекста обращения и видео: более поздние решения задач отменили соответствующие части ранней спецификации и документации.
- Публикации используют расширенный Markdown, самостоятельную календарную дату, стабильные slug и собственные редакционные разрешения. Стандартные настройки WordPress не гарантируют эквивалентности.
- Существование ранее созданных тестовых публикаций и медиа зафиксировано в журнале; по ответу пользователя перенос из Strapi исключён из объёма работ.
- FTP переносит файлы; WordPress дополнительно требует создания/настройки базы, а при переносе существующего наполнения — импорта данных и настройки адреса сайта.

## Ответы первого раунда

1. Строго WordPress 6.7.1. Пользователь может предоставить файлы установленного комплекта Timeweb, если они потребуются.
2. Сохранить внешний вид и поведение, PHP + CSS + небольшой JavaScript.
3. Только публикации доступны для редактирования через CMS.
4. Новая локальная база, без импорта из Strapi. На хостинге планируется штатное использование существующей установки и БД после уточнения способа подключения.
5. Весь локальный стек в Docker, с короткой инструкцией обновления/пересборки.

## Ответы второго раунда

6. Пользователь не определяет техническое устройство установки; на хостинге предположительно чистый базовый WordPress. Адаптация к нему — задача реализации после осмотра.
7. Сохранить Markdown, только если он поддерживается редактором WordPress.
8. Использовать стандартную роль WordPress «Автор».

## Ответ третьего раунда

9. Использовать готовый Markdown-плагин; проверить, что он бесплатный.

Найден готовый плагин Markup Markdown: по документации автора он заменяет редактор на EasyMDE, хранит Markdown и формирует HTML через PHP. Его совместимость именно с WordPress 6.7.1 и соответствие расширенному синтаксису проекта пока не проверены и не заявляются подтверждёнными. Выбор конкретной версии плагина требует проверки на целевом стеке; нельзя считать перечисленные в прежней спецификации Markdown-расширения поддержанными автоматически.

Проверка бесплатности: плагин доступен для свободного скачивания в WordPress.org как открытое ПО. По опубликованному описанию для написания/публикации Markdown нет обязательной оплаты или подписки. На странице поддержки автор отдельно предлагает платную профессиональную поддержку и разработку функций; это дополнительные услуги, а не лицензия редактора.

Реальное ограничение: раздел Accessibility на странице плагина сообщает о несовместимости текущего интерфейса с вспомогательными устройствами, включая скринридеры. Это относится к редактору админки, а не является оценкой доступности публичного сайта.

## Ответ четвёртого раунда

10. Авторы не будут пользоваться скринридером. Это ограничение редактора Markup Markdown не блокирует выбор. Требования к доступности публичного сайта сохраняются.
