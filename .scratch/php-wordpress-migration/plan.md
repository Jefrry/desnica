# План миграции на PHP и WordPress

Status: ready-for-agent

Сопроводительный план к опубликованной [спецификации](spec.md), оформленной по вызову to-spec. Реализация не начата. Разделение этапов на отдельные задачи в `issues/` выполняется следующим шагом.

## 1. Минимальная среда для работы над публичным сайтом

- Создать отдельный каталог `wordpress/` с собственным Compose-файлом, темой и плагином правил сайта. Существующие приложения и файлы сохранить.
- Подготовить строго WordPress 6.7.1, PHP 8 и MySQL в контейнерах через Podman. Собственный Compose-файл должен быть проверен выбранным способом запуска с Podman; Docker Desktop и Docker Engine не требуются. Выбрать и закрепить конкретные версии PHP/MySQL с учётом проверки Timeweb; предварительный ориентир PHP 8.3 и MySQL 8.0 не является подтверждением конфигурации аккаунта.
- Проверить Podman и необходимое ему локальное окружение Windows, способ запуска Compose и обеспечить запуск сервисов. Наличие и работоспособность Podman пока не проверены; отсутствие команды Docker не является блокировкой. Если понадобится установка ПО или изменение системных компонентов, выполнить это по отдельной инструкции с необходимыми разрешениями.
- Подключить исходники темы/плагина с компьютера, чтобы обычные изменения не требовали пересборки. Хранить MySQL в отдельном постоянном томе. Старый Compose и том PostgreSQL не менять.
- Добавить очень короткий README с проверенными командами для Podman: первый запуск, обновление страницы после обычных правок, пересборка после изменения окружения, остановка и повторный запуск с сохранением данных. Указать проверенные адреса сайта и админки. Не предлагать удаление тома базы как обычный способ обновления.

Приёмка: чистая установка запускается через Podman, данные сохраняются после перезапуска, PHP-правки темы видны без пересборки. Проверены подключения исходников, сеть сервисов и постоянные тома в фактическом окружении Podman на Windows. Этот этап — необходимая основа, а не перенос всей админки до публичной части.

## 2. Публичная часть — главный приоритет

- Перенести общую структуру страниц, шапку/подвал, меню, типографику и мобильное поведение в классическую PHP-тему с CSS и небольшим JavaScript.
- Последовательно перенести главную, раздел об организации/миссии/документах/отчётах, услуги и четыре услуги, обучение, НКО, контакты и правовую страницу.
- Сохранить существующие URL, query-параметры, якоря, выбор документов/отчётов, клавиатурное управление и навигацию назад/вперёд.
- Перенести внешний вид архива и страницы статьи. При пустой базе показывать корректное пустое состояние; проверочные материалы использовать только в явно отдельной локальной проверке.
- Сохранять текущий объём функций: форму отправки, карту и удалённые ранее возможности не возвращать. Существующие отсутствующие материалы не заменять выдуманными реальными данными.

Приёмка: публичные страницы сравниваются с текущей версией на настольных и мобильных размерах, проверяются клавиатура, фокус, 404, отсутствие ошибок PHP/JavaScript. Проверяется существующая политика запрета индексации по умолчанию.

## 3. Публикации и Markdown

- Проверить и подключить готовый бесплатный Markup Markdown с WordPress 6.7.1/PHP 8. Пользователь подтвердил, что авторам не требуется скринридер; документированное ограничение редактора принято. Если проверка на целевом стеке выявит несовместимость, подобрать бесплатный совместимый вариант, сохраняя согласованные редакционные возможности; существенные отклонения согласовать.
- Использовать штатные записи WordPress и стандартную роль «Автор». Не расширять её права до редактирования чужих статей.
- Сохранить отдельную календарную дату публикации, заголовок, анонс, обложку/alt, стабильный slug, архив по 6 записей, оглавление и возврат к архиву. На публичном сайте показывать только опубликованное.
- Проверить расширенный Markdown на существующей фикстуре проекта. Недостающие возможности согласовать или реализовать в плагине сайта; нельзя молча исключать таблицы, сноски или специальные блоки.
- Обеспечить единую обработку Markdown для отображения и оглавления без повторного преобразования HTML. При одинаковой дате использовать стабильную сортировку с ID WordPress, так как переноса Strapi нет.

Приёмка: создание, сохранение, повторное открытие, предпросмотр и публикация статьи работают от роли автора; черновики недоступны публично; чужие записи не редактируются. Проверены Markdown, изображения, даты, пагинация, устойчивость URL и очистка опасного HTML.

## 4. Установка в существующий WordPress Timeweb

- Проверить фактические версии PHP/MySQL, WordPress 6.7.1, список плагинов, структуру установки и правила адресов. Сейчас панель требует входа, и эти факты не проверены.
- Подготовить готовый к загрузке комплект темы, плагина сайта и бесплатного Markdown-плагина с необходимыми зависимостями. Node.js, Composer и Docker на хостинге не должны требоваться.
- Описать резервное копирование перед активацией, загрузку по FTP, активацию через админку и минимальную настройку адресов/маршрутов.
- Использовать существующий `wp-config.php` и подключение к базе. Не заменять их локальными файлами и не импортировать локальную базу поверх хостинговой. Существующие базовые записи не удалять автоматически.
- Зафиксировать целевую версию ядра 6.7.1 в локальном окружении и инструкции; отдельно проверить, не обновляет ли её автоматически установщик/панель хостинга.

Приёмка: сайт и редактор работают на хостинге, маршруты открываются напрямую и после обновления страницы; загрузки доступны, локальные адреса отсутствуют, база и администратор установки сохранены.

## 5. Итоговая проверка

- Сопоставить все публичные маршруты и ключевые сценарии с текущим сайтом.
- Проверить мобильную версию, клавиатуру, увеличение текста, публикации/черновики и роли. Проверку вспомогательными устройствами не считать выполненной без фактического прогона.
- Проверить короткие инструкции локального запуска/обновления и FTP-установки на подготовленном комплекте.
- Записать результаты и оставшиеся ограничения в отдельные задачи. Старую реализацию не удалять.
